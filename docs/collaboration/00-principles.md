# 协作原则：最简路径优先

## 为什么要写这条

历史教训：性能优化太难时会不停换路线，第一次没找对方向就造成大量无效投入；团队若无统一记录，还会重复踩坑。

本仓把「找路」变成**可审计、有时限、可交接**的流程。

## 四条铁律

### 1. 正确性底座先于性能

没有稳定通过的功能/精度基线，任何性能改动都不算「优化」，只算「赌博」。

### 2. 默认走最简方案

「最简」指：

- 最少新抽象、最少特殊 case 分叉  
- 优先复用 AscendC 常规范式（Host/Kernel 分离、标准 tiling、全核参与）  
- 能用任务书豁免（小 shape 仿真分析）就不要硬抠

达标即停；超额优化需 Owner 书面批准并记账。

### 3. 一条主路径 + 有界实验

同时只允许 **1 条主开发路径**。  
并行实验最多 1 条，且必须：

- 独立分支/目录标记 `exp/`  
- 写入台账时限  
- 到期合并结论或废弃，禁止无限挂起

### 4. 记忆优于口头

台账 > 会议纪要 > 聊天。  
未写入 `path-ledger.md` / `dev-log.md` 的结论，交接时可以当作不存在。

## 决策优先级

```text
任务书硬门禁
  → 功能/精度必须过
  → 性能：全核场景 ≥ TBE 95%（以本题为准）
  → 小 shape 豁免条款（若任务书有）
  → 额外炫技优化（默认不做）
```
