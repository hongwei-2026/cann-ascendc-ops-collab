## 结果

35个启用输入全部六轮改善。[8,64,3]完整Task：FP32 10.64→6.51μs（38.82%）、FP16 11.33→6.06（46.51%）、BF16 11.25→6.215（44.76%）。2826次逐调用双输出精度再次通过。

原J061的FP32[4,6,8]如今回退原路径，4.2775→4.30μs且六轮控制通过。J061两项FP16 S=1回退在本次恢复：[127,64,1]6.38→6.37、[127,8192,1]11.76→11.74μs，各六轮控制通过。

**仍不能晋升整包：251/270控制组通过。** 同样两种S=1形状本次BF16出现6.38→7.58μs（慢18.81%）和12.0075→12.62（慢5.10%），均六轮回退。另有BF16 S33小控制边界变化和两组长FP16输入A/A/C漂移，完整19组保存在control-failures.json。A/A最大0.48μs来自长输入，原始固定0.1μs且2%双门槛不改。

结论：跨通道合批方向有明显有效性；两项结构修正解决了无合并机会的小输入和原FP16控制，但“删掉无效key即可关闭所有连带回退”未成立。不能断言已证明缓存/编译布局是根因，不把BF16退化忽略，也不重复刷新门槛。停在此处归档，不继续自主开新实验。当前代码是诊断实验，不是替代提交包。

## 唯一源码修正

相对J061，short_s.h与Host逐字一致，只在p_relu_grad_update_b.cpp更改两项入口条件：
1. 仅在blockFactor>innerSize时启用，确保存在跨通道合并机会。
2. 编译期限定schMode必须匹配实际DTYPE_GRADS，避免把不使用的dtype/key stub展开成几KB。

其余算法、UB、周期相位、masked Duplicate、Compare+Select和CAST_RINT都未改。dispatch-only.diff给出精确差异；包名J061→J062只用于私有构建隔离。本轮只复用原45性能输入，实际启用数由36变35，没扫描shape阈值、tile或核数。
