# J027：13 μs 大输入的 IO 核算、缓存诊断与权重转换实验

执行日期：2026-11-05（云端 UTC+08）。环境仍为 Ascend910_9362 / ascend910_93 / dav-c220-vec、40 Vector 核、CANN9.0.0、driver25.5.5。基线J026保留，未提交竞赛、未push、未改网络或安全设置。

## 本轮限定范围与结果口径

只实现一个候选J027：低精度split-C首batch转换权重到FP32后驻留；复用已有neg缓冲保存转换结果，Compare完成后复用已失效的featuresFloat保存weight*grad。Host、tile、核数、UB分配不变，数学仍Compare+Select，不改舍入和输出定义。708组原有设备精度全部通过。所有新对照使用既有输入，不能把它们重新称为独立留出。

参考了 [hicann/ops-nn固定commit的PReLU实现](https://github.com/hicann/ops-nn/blob/b5f577d6bfdbc543d42638ef8635e3f5ef8cb0c8/experimental/activation/prelu/op_kernel/prelu.h)：CopyWeightTile将BF16权重转成FP32，ProcessChannelNcSplitCWeightReuse仅在通道块变更时重建权重向量。该上游是ascend910b实验PReLU、单输出，许可CANN Open Software License Agreement Version2.0；本次仅借鉴生命周期思路，没有直接移植。原文和许可见J021留档。features缓冲复用也参考本项目J008，未重做已失败的J007缩小tile双缓冲扫描。

J027IO是诊断版本，保留J026分块、输入权重搬运、队列、循环、输出搬运，移除算子数学，用两次UB DataCopy把grads/features原样写到dx/update。它只做identity输出校验，**不是有效的PReluGradUpdate候选，也不是严格硬件下界**；UB拷贝和指令组合、输出数据内容均与实际算子不同。

普通msprof PipeUtilization：63数据集×2算子版本×4轮=504组，3形状×3dtype×4轮=36组IO诊断；每组150次、取101–150次中位数，共81000条profile。原始参数次序与逐轮数据全部保留。另有24次msprof op缓存诊断，以及4个固定数据集的四轮A/B/A夹测（48组输出、12000条普通profile）。合计93000条普通profile、24次单算子profiler运行；算子输出与IO identity输出分开统计。708精度和所有对应输出校验均通过。有限随机数据及零值验证，不扩大为NaN/Inf或所有可能输入证明。

主表为msprof Task Duration(us)设备任务时长，各轮中位数的均值，非主机API端到端时间。AIV、Vector、Scalar、MTE活动可重叠，不相加；Task减AIV的差也不能直接称CPU启动开销。普通profiling和两种replay的结果分别展示，不混成同一分布。

## 数据量、带宽与条件下界

令E=N*C、元素字节数b，接口至少读grads/features并写dx/update，权重唯一读取C个元素，因此理想逻辑流量 `Qmin=(4E+C)*b`。J026按通道块与batch分组复用权重，计划逻辑流量 `Q=(4E+G*C)*b`，G=floor(40/ceil(C/maxTile))。这是GM接口流量模型，不是实际HBM流量；缓存命中、写回和分配流量会改变各存储层承担的字节。

对[127,8192,1]，E=1,040,384，G=20：低精度Qmin=8,339,456字节、Q=8,650,752；FP32分别16,678,912和17,301,504字节。上一轮J026低精度约13.1–13.3 μs对应计划逻辑吞吐0.65–0.66 TB/s，FP32约12.18 μs对应1.42 TB/s。要在5 μs处理同样Q，需要低精度1.73、FP32 3.46 TB/s；4 μs则2.16/4.33 TB/s。

只有当所代入带宽B确实适用于承担该流量的存储层时，`Qmin/B`才是相应条件下界。以下是情景计算，**不是本机峰值规格**：

| 假设有效带宽 | FP16/BF16 Qmin/B | FP32 Qmin/B |
|---|---:|---:|
| 1 TB/s | 8.339 μs | 16.679 μs |
| 1.5 TB/s | 5.560 μs | 11.119 μs |
| 2 TB/s | 4.170 μs | 8.339 μs |
| 3 TB/s | 2.780 μs | 5.560 μs |

本机平台配置记录L2=176160768字节（168 MiB）、memory_size=32 GiB；ddr_rate=32等字段缺少已核实单位，未据此换算峰值。没有取得能绑定当前逻辑设备的官方HBM峰值，因此不拿网上整卡宣传值直接判定5 μs可达或不可达。工作集只有数MB，重复调用可能主要经过L2；下文用实测命中率区分。

## 结论与下一步

本轮保留J026为基线，J027作为待进一步验证的低精度条件候选；不全局替换。J027不是简单的“无收益”：普通63组协议未见稳定收益，但固定分配顺序的A/B/A协议在目标大输入得到低精度四轮一致改善。两个协议不同，不能挑选最快值当成普适结果。

| FP16 | 12.555 | 11.890 | 12.925 | -0.850 |

未改的FP32 [600000,1,1]也出现-0.341 μs差值。A2相对A1系统性偏慢约0.16–0.46 μs，说明固定A/B/A顺序仍存在状态或执行位置效应。不能直接用FP32偏差扣除低精度得到“净收益”，但低精度额外改善与Vector减少0.384/0.430 μs相符，支持机制有效；总体泛化收益尚未证实。当前只确认分配顺序固定，不声称不同进程得到相同物理地址。

### 13 μs主要花在哪里

同一[127,8192,1]，两轮msprof op结果：

| dtype | 完整J026：保留L2 / 清L2 | IO诊断：保留L2 / 清L2 |
|---|---:|---:|
| FP16 | 12.920 / 14.700 | 8.240 / 9.750 |
| BF16 | 12.760 / 14.750 | 7.970 / 9.590 |
| FP32 | 11.800 / 14.480 | 8.780 / 11.000 |

保留L2时读命中率约99.997–99.999%、写命中100%；清L2时读约7.14–7.34%、写约0.25–0.49%。这些样本CurrentFreq均1650 MHz。FP32清缓存时MTE2每轮最大核活跃时间为7.564/7.081 μs，Vector为3.864 μs；保留缓存时MTE2为3.307/3.364 μs，Scalar为7.773/7.533 μs。低精度保留缓存时Vector约5.497（FP16）/5.718（BF16）μs，Scalar约6.18–8.01/6.75–7.69 μs。这里各指标取各自最大核，不一定同一核，且有重叠，不能拼成耗时饼图或独占占比。

因此冷缓存大输入明确要关注MTE2；热缓存仍有循环、队列、同步与向量执行成本。移除数学计算的诊断路径仍约8–9 μs，是当前结构代价的直接证据，但它改变了指令混合，不是严格的硬件下界。权重Cast只能减少其中不足1 μs的Vector工作，单靠它不能解释13→5 μs的差距。

### 下一项最有依据的有限实验（本轮未实现）

只对低精度split-C路径尝试**保持原tile大小的输入预取双缓冲**，第二套buffer仅给grads/features，权重与输出队列不变。目标是用下一batch的MTE2覆盖当前Vector/输出阶段，而非再次扫描核数或缩小tile。先以同一IO诊断验证是否确实改善调度/搬运，再验证真实算子。此前J007改变tile导致循环数增加；本提案控制tile不变，检验的是不同假设。

从当前InitBuffer逐项核算，低精度原35 B/元素，新增两份2 B输入后为39 B/元素；最大tile4288需要167232 B，小于物理UB196608减8192保留后的188416 B，余21184 B。当前80%预算为150732 B，实施时须显式调整该专用路径预算/检查，不能沿用错误的35 B核算。FP32最大tile5184若同样增加输入槽需191808 B，超过188416 B，故不直接推广到FP32。

限定成本：一个真实候选加一个诊断候选，固定3个现有大输入和少量未使用的相邻形状；先诊断四轮交替，如果无一致改善即停止，不做参数网格。若诊断有效，再做三dtype完整708组回归（FP32路径不改）及留出形状、交替性能；预计实现/构建/验证约20–30分钟，设备作业约5–10分钟，归档另计。接受标准是完整输出正确、同协议收益超出A/A状态差异、未改路径无可复现回退。4–5 μs仍是目标，当前没有证据承诺达到。
