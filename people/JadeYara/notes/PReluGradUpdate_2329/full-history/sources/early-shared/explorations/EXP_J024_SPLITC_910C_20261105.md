# J024：split-C 跨 batch 复用权重，910C 实测

执行日期：2026-11-05（云端 UTC+08）。**J024 在 `[127,8192,1]` 三种 dtype 上取得四轮一致收益：热态 FP16/BF16 约快 27%，FP32 约快 16%。但 `[31,32768,1]` 低精度有四轮一致回退，当前保留为专项实验候选，不替换综合版本。** J013/J018/J020/J022/J023 与原始证据均保留，未提交竞赛、未 push。

## 为什么选这个改动

J023 的大输入变动主要伴随 MTE2/MTE3 指标变化，而同形状 Vector 时间相对固定。J018 的驻留分支要求完整 C 权重能放入 tile；本机最大 tile 为 FP32 5184 元素、FP16/BF16 4288 元素，C=8192 及以上不能直接使用该方案。因此本轮把通道分块，再让每个通道块连续处理多个 batch，摊薄权重搬运。

上游线索来自 [hicann/ops-nn 的 ProcessChannelNcSplitCWeightReuse](https://github.com/hicann/ops-nn/blob/b5f577d6bfdbc543d42638ef8635e3f5ef8cb0c8/experimental/activation/prelu/op_kernel/prelu.h)，固定 commit `b5f577d6bfdbc543d42638ef8635e3f5ef8cb0c8`。其实现按通道块遍历 batch，仅在块变更时装载/构造权重向量。许可为 CANN Open Software License Agreement Version 2.0；原 experimental PReLU 注册 ascend910b，只有一个输出，不能视为本算子/910C 直接兼容实现。本轮只借鉴调度思路，用自己的 J018/J023 计算与拷贝代码实现；原文及许可已留在 J021 上游对照记录中。

## 具体改动与资源核算

基于 J023，增加独立 split-C 内核与 tiling key 16/17/18，新增 splitBatchGroups 字段，保留原有 12 个 key 和 dtype 编译期裁剪。适用条件为按通道权重、S=1、C 满足 32 字节对齐、C 超过 maxTile、通道块数不超过 40 核，以及每个 batch 分组至少有两个 batch。规则使用规模/对齐条件，没有按已知测试 shape 特判。

`cTiles=ceil(C/maxTile)`，`batchGroups=floor(40/cTiles)`，使用 `cTiles*batchGroups` 核。每个核持有一个通道块权重，在分配到的连续 batch 区间逐行计算，首行装载权重后复用。tile 按 64 元素对齐，尾通道块独立裁剪；两输出仍为逐元素 dx/update，不新增跨 batch 归约，也不改变正负分支语义。

本机物理 UB 196608 字节，保留 8192 后以 80% 预算计算 maxTile（150732 字节）。C=8192 时，两块各 4096，20 个 batch 分组，共 40 核；FP32/低精度估计 UB 为 118784/143360 字节。N=127 时每核处理 6 或 7 行。相对逐元素读取权重的逻辑模型，权重加载元素数从 N*C 降为 batchGroups*C，少 84.25%；总输入搬运元素数少 28.08%，含两个输出的总 GM 元素数少 16.85%。这些是逻辑流量估算，不是实测 DRAM 字节数，L2 与地址映射仍会影响实际收益。

C=32768 时 FP32 分成 7 块、每块 4736 元素、35 核；低精度分成 8 块、每块 4096、40 核。并行度、尾块、循环次数和 batch 负载平衡也随之改变，不能把全部时间收益仅归于权重流量减少。
