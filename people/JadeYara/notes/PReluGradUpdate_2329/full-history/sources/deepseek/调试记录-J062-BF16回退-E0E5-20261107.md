## 1 云端连接恢复（先决条件）

### 1.1 根因（已定位）

`ssh <alias>` 的 AtomGit 门禁每次都失败，原因不是云端宕机、也不是主机指纹：

1. `ssh` 命中配置里的 `Match originalhost … !exec "cmd.exe /d /c call …\forward-bootstrap\<id>.cmd"`，该 helper 必须运行；
2. helper 是 `Code.exe`（`ELECTRON_RUN_AS_NODE=1`）+ `forward-bootstrap.js`，必须在 `C:\Users\lin\.atomgitdevenv` 下写**锁文件、日志与状态**；
3. 当前 DSH 会话是 `workspace-write` 文件沙箱，**拒绝写 `C:\Users\lin\.atomgitdevenv`**；
4. helper 因此静默 exit 1（无新 `bootstrap.log` 记录），ssh 走 `ProxyCommand exit 1`，报 `Connection closed by UNKNOWN port 65535`；
5. VS Code 不受该沙箱限制，所以 09:40/09:54 能连，而普通 shell 的 ssh 一直失败。

验证证据：
- `New-Item C:\Users\lin\.atomgitdevenv\__sandbox_write_test__` → `Access denied`；
- 沙箱内直接 `node forward-bootstrap.js --config …` → exit 1，`bootstrap.log` 无新增；
- 放宽一次文件沙箱后，`bootstrap.log` 立刻出现 `forwardBootstrap.forward.ready localPort=31930 remotePort=22`（2026-11-07T02:08:10Z），同一次命令内 ssh 连接成功。

## 3 E7（顺带）：kernel `.o` 机器码字节级对比

从云端取回 J062 包内 4 个 kernel 对象（bf16/fp16 × A/B 别名），本地用自写 ELF 解析器提取 15 个 tiling-key 入口函数体并逐字节比较。

| dtype | 函数（tiling key） | A 字节 | B 字节 | 差异 |
|---|---|---:|---:|---|
| bf16 | default (0/2/…) | 4468 | 9568 | 因 J062 新增 ShortS 实例化而变长 |
| bf16 | S1 (6) | 5064 | 5064 | **仅 2 字节 / 1 个 4B word** |
| bf16 | MERGED (10) | 5452 | 5452 | **仅 2 字节 / 1 word @+0x204** |
| bf16 | RESIDENT (14) | 7068 | 7068 | 仅 2 字节 |
| bf16 | SPLITC (18) | 7072 | 7072 | 仅 2 字节 |
| fp16 | default (1) | 4648 | 10116 | 因 ShortS 变长 |
| fp16 | S1/MERGED/RESIDENT/SPLITC | — | — | **同样各仅 2 字节** |

两处差异 word 示例（MERGED）：
- bf16：A `0x070a5594` → B `0x070a51a8`（差 -1004）
- fp16：A `0x070a54c4` → B `0x070a5f68`（差 +2724）

**判读**：S=1 输入实际执行的 MERGED 函数，其机器码在 A/B 之间只有 **一个带立即数/相对地址的指令 word** 不同（随函数在 `.text` 内整体平移而变化，属重定位型差异），其余指令逐字节一致。**因此"J062 让 BF16 路径的指令数变多/代码生成恶化"这一解释不成立。**

## 5 结论与假设台账更新

| 假设 | 调试前 | 调试后 |
|---|---|---|
| H1 指令放置/取指开销 | 最可疑 | **部分支持但需改写**：现象是 per-process 的，且与 `icache_miss_rate` 无关；更像 kernel 二进制的**每进程加载/放置/首次执行状态**，不是稳态取指 miss |
| H2 同源码 codegen/指令数差异 | 可能 | **排除**：执行函数机器码 A/B 仅差 1 个立即数 word；且 P2/P3 无慢点 |
| H3 别名/加载/测量层 | 部分可能 | **支持**：同一组二进制在不同进程表现不同；P1 的 B 偏慢与 P2/P3 的 B 正常互斥于"代码属性"解释 |
| H4 BF16 走另一模板实例 | 基本排除 | **排除**（源码级 + 机器码级） |
| H5 UB/tiling 参数变化 | 基本排除 | **排除**（block_nums/tiling/地址一致） |

**最终判读**：J062 的 "BF16 S=1 未改路径回退" 是**单进程伪影**（per-process runtime/placement effect），在两次独立重跑中完全消失；不能作为否定 J062 算法收益的证据。J062 的启用输入收益（35/35、210/210 轮）在三个进程均稳健。

**同时暴露的协议问题**：FP16 两个长输入（`[257,257,3]` 677 µs、`[2048,9,5]` 193 µs）的 A/A 绝对漂移在三个进程都出现（0.12–0.48 µs，相对 <0.1%），按现行"≤0.1 µs 且 ≤2%"双门槛必然失败。这是**测量口径限制**，不是候选缺陷；本轮按规则记录，未改门槛、未重测刷过。
