# J039：两次 Select 间外层同步验证

保留 J035/J038，只删除 split-C 中第一条 count Select 后的一处外层 PipeBarrier<PIPE_V>()。没有更改系统头文件、编译同步开关、UB布局、算术、tiling、分核、队列或其他同步。未提交比赛或 push。

## 数据依赖与官方安装实现

J038 两次 Select 的数据依赖：

| 调用 | 读取 | 写入 |
|---|---|---|
| update Select | mask、常驻 zero、fg | updateFloat |
| dx Select | mask、grads、neg | dxFloat |

两组写入与对方的读写集合不重叠，共用 mask 是只读。更直接的证据来自**本机 CANN9 官方安装头文件**，而非只看应用层别名：

- `aarch64-linux/asc/impl/basic_api/kernel_operator_vec_cmpsel_intf_impl.h:561` 的 count 重载调用 `VselImpl(..., count)`，SHA256 `3b5fdf9fddf468b8a37f1a1c8ad4e0c529db2220d6facec33cd076996d06f2b8`。
- `aarch64-linux/asc/impl/basic_api/dav_c220/kernel_operator_vec_cmpsel_impl.h:178–198` 的模式2实现依次准备临时UB中的mask地址、Duplicate、PIPE_V、set_cmpmask、PIPE_V、vsel、**PIPE_V**，然后恢复mask状态。SHA256 `9a0e66e77d4e6dac930b0a9913ba560695d8d29b9d08fdeaad41a4ca0a323705`。
- 因此第一条 count Select 返回前，API内部已经等待相关V流水完成；外层再次等待属于重复候选。内部CMPMASK/临时UB同步全部保留。结论限定于实际检查的 CANN9/dav-c220 count重载，不推广到别的重载或架构。

此前 J038 建议强调“常驻零消除 dx 别名”，这个解释不完整：实际 count API 的内部同步更关键，J035 的该别名也已由内部同步排序。不能将删一行源码直接等同于减少一条有效硬件同步。

[官方 PipeBarrier 页面](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910beta2/API/ascendcopapi/atlasascendc_api_07_0271.html)提供同步和自动同步参考，但网页正文抽取未成功。本轮判断以已读取并归档的安装头文件、编译产物和设备结果为准，没有用第三方博客替代官方实现。头文件快照和哈希在归档 `J039-api-evidence`。

## 正确性与压力

环境为 Ascend910C / ascend910_93 / dav-c220-vec，CANN9.0.0，driver25.5.5，40 Vector核。启动前 NPU 空闲，J038 两个设备作业均退出0。

756 个既有用例，加三 dtype × 两个新输入 `[81,8256,1]`、`[97,10336,1]` × 四种掩码模式，共 **780 个精度用例全部通过**。新输入 seed390081，四种模式为逐元素正负交替、每64元素交替、跨batch整段正负翻转、通道维最后129个位置为负；每64元素末位另置零。保留不同梯度和逐通道权重，覆盖 CMPMASK 边界、零点、跨batch更新和非整齐尾部。仅有限值测试，不宣称覆盖所有IEEE特殊值。

已有33个压力输入各64次，新24个针对性输入各128次，合计 **5184 次调用**；每次均取回并检查 dx/update，共10368个输出检查全部通过。

## 结论与下一方向

**结论：本轮验证了这处外层同步在已测 CANN9/dav-c220 路径上的冗余性，但没有证明性能收益。J039 留作实验版本，继续保留 J035 基线和 J038 候选，不升级为更快版本。**

33 个 shape/dtype 组合中，四轮都更快为 0，四轮都更慢也为 0。各组合均出现方向翻转或持平。J038 同版本 A/A 顺序差为 −1.559 至 +2.360 μs，J039 B/B 为 −1.920 至 +2.0105 μs；这些是同轮两次运行的有符号差，不是置信区间。它们明显大于本轮多数 A/B 均值差，说明普通整核计时仍受运行顺序或设备状态影响，不能用微小均值差认定收益。

代表输入 `[127,8192,1]`，权重长度8192，四轮配对统计均值：

| dtype | J038 μs | J039 μs | J039−J038 μs | 四轮方向 |
|---|---:|---:|---:|---|
| FP32 | 10.886250 | 10.812313 | −0.073938 | 快、快、慢、快 |
| FP16 | 11.833563 | 11.772375 | −0.061188 | 快、慢、快、快 |
| BF16 | 11.902500 | 11.854688 | −0.047812 | 快、快、慢、快 |

FP16/BF16 的机器码逐字节相同，Compute 分段周期也分别固定为1163/1227，表中小幅下降不能归因于源代码删除。FP32 虽然机器码变化，Compute 分段却从857–858周期变成866周期，两个反向顺序轮次一致略慢；这也不支持优化成立。未修改的 `[600000,1,1]` FP32 控制路径均值也下降约0.0728 μs，与目标 FP32 的下降量接近。

因此停止继续删除这处外层 barrier 的性能扫描。保留结果作为“正确性通过、没有可复现加速”的反例。已确认的细节是 count Select 内部已有结束同步，而不是两次 Select 在所有接口/架构上都可以不做同步。下一步应考察接口内部重复的 mask 状态配置；具体可测方案和必要条件如下，尚未实施。


新的有依据方向是减少 **count Select 接口内部重复的掩码状态配置**，而非继续机械删除外层barrier。本机公开的repeat重载（同一接口文件504–521、dav-c220实现252–264）走 `VselIntrinsicsImplPre` 和 `VselIntrinsicsImpl`，与count路径的 SetMaskCount/ResetMask/SetMaskNorm 序列不同。split-C 的 cmpCount 已按64个float对齐，最大5184，即至多81个repeat，可构造固定64元素mask和正常stride的候选。

该方向尚未改代码或实测，仍需核对模式2掩码跨repeat推进和保持必要同步；可直接用本轮24个针对性用例先验证，再做780回归及交替对照。保留 Compare(+zero)，不重走历史失败的CompareScalar路线，不直接使用私有intrinsics或覆盖系统头文件。若该公开API改法也不减少实际指令/周期，就停止该方向；目前不承诺其收益。
